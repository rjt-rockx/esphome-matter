Some Matter clusters are not plain attribute stores: the connectedhomeip SDK drives them through an application delegate. Without one the cluster exists in the data model but cannot be operated: the mode clusters have no `ChangeToMode` command and an empty `SupportedModes`, Operational State has no `Start`/`Stop`/`Pause`, and a controller sees an appliance that never changes state.

This page covers the delegate layer of the component for

* every **Mode Base** derived cluster: Laundry Washer Mode, Dishwasher Mode, RVC Run Mode, RVC Clean Mode, Refrigerator And Temperature Controlled Cabinet Mode, Microwave Oven Mode, Energy EVSE Mode, Water Heater Mode, Device Energy Management Mode, plus **Mode Select**
* **Operational State** and **RVC Operational State**
* **Laundry Washer Controls** (spin speeds and rinses)

Energy EVSE, Device Energy Management and Service Area need much larger delegates; see [design/delegates-evse-dem.md](design/delegates-evse-dem.md).

The delegates are configured under the `clusters:` of an endpoint, next to the device type that creates the cluster:

```yaml
matter:
  endpoints:
    1:
      laundry_washer: {}
      clusters:
        laundry_washer_mode:
          modes:
            - {label: Normal, tags: [normal]}
            - {label: Delicate, tags: [delicate, quiet]}
            - {label: Heavy, mode: 10, tags: [heavy, max]}
          select: washer_program          # optional, two-way
          on_change_to_mode:              # optional
            - logger.log:
                format: "washer program %d"
                args: [mode]
        operational_state:
          phases: [Pre-wash, Wash, Rinse, Spin]
          state: washer_state             # a select or text_sensor
          countdown_time: washer_remaining
          on_start:
            - switch.turn_on: washer_start
          on_stop:
            - switch.turn_off: washer_start
```

Device types that create a delegate-driven cluster without it being configured (for example `robotic_vacuum_cleaner` creates RVC Run Mode and RVC Operational State) log a warning during validation: such an endpoint is structure only.

# Mode clusters

```yaml
clusters:
  rvc_run_mode:                # any Mode Base derived cluster, or mode_select
    modes:                     # required, 2 to 255 entries
      - label: Idle            # required, 1 to 64 bytes, unique
        mode: 0                # optional mode number (0-255); defaults to the position in the list. Unique
        tags: [idle]           # required (1 to 8). Tag names, numbers or {mfg_code, value}
        option: Idle           # optional: the select option for this mode (defaults to label)
      - {label: Cleaning, tags: [cleaning]}
    select: vacuum_run_mode    # optional ESPHome select
    on_change_to_mode:         # optional automation, variable `mode` (uint8)
      - ...
```

The mode list is encoded as `SupportedModes`. `CurrentMode` is kept by the SDK in non-volatile storage; the first mode is used when nothing was stored.

## Tags

A mode needs 1 to 8 semantic tags and at least one of them has to be a tag from the Matter specification. The tag names are the snake_case names of the specification: the common tags `auto`, `quick`, `quiet`, `low_noise`, `low_energy`, `vacation`, `min`, `max`, `night`, `day` and the ones of the cluster (`normal`, `delicate`, `heavy`, `whites` for the laundry washer, `idle`, `cleaning`, `mapping` for the RVC run mode, ...). An unknown name lists the available ones. The data comes from `components/matter/data_model/delegate_data.json` (generated by `tools/gen_delegate_data.py`).

Manufacturer tags are a number in `0x8000`-`0xBFFF`, or `{mfg_code: 0xFFF1, value: 7}`.

The specification (and the Matter certification tests) require some tags and the component checks them when validating the config:

| Cluster | Rule |
|---|---|
| `laundry_washer_mode`, `dishwasher_mode`, `microwave_oven_mode` | a mode with the `normal` tag |
| `energy_evse_mode` | a mode with `manual` |
| `water_heater_mode` | a mode with `manual` and one with `off`; a mode has at most one of `off`, `manual`, `timed` |
| `rvc_run_mode` | a mode with `idle` and one with `cleaning`; a mode has at most one of `idle`, `cleaning`, `mapping` |
| `rvc_clean_mode` | a mode with `vacuum` or `mop` |
| `device_energy_management_mode` | a mode with `no_optimization`, which is not combined with the other optimization tags |

> YAML turns an unquoted `off`/`on` into a boolean. `tags: [off]` works (the component maps it back), a label has to be quoted: `label: "Off"`.

## Select binding

With `select:` the ESPHome select and `CurrentMode` are kept in sync in both directions:

* a controller's `ChangeToMode` is accepted, the select is set to the `option` of the mode (default: the label), and `on_change_to_mode` runs;
* changing the select (a button, an automation, a Home Assistant user) updates `CurrentMode`.

Every mode needs an option in the select. If the options of the select are known when the config is validated (template and most other selects), a missing option is an error. The select is the source of truth after a restart: its restored state replaces the stored `CurrentMode`.

## on_change_to_mode and ChangeToModeResponse

A `ChangeToMode` command is answered *synchronously* by the CHIP task, but ESPHome automations run on the main loop. The component runs `on_change_to_mode` on the main loop and waits (at most 750 ms) until the automation's synchronous part has finished. If it called `matter.mode.reject`, the controller receives that status, otherwise `Success`:

```yaml
on_change_to_mode:
  - if:
      condition:
        lambda: 'return mode == 1 && id(dust_bin_full).state;'
      then:
        - matter.mode.reject:
            status: dust_bin_full        # a status name of the cluster, or a number
            text: Empty the dust bin first
```

`status` is `generic_failure` by default; `invalid_in_mode` is the other generic one. The clusters add their own: `stuck`, `dust_bin_missing`, `dust_bin_full`, `water_tank_empty`, `battery_low`, ... for the RVC run mode, `cleaning_in_progress` for the RVC clean mode (see `delegate_data.json`). Actions after a `delay:` are not part of the decision. The SDK answers `UnsupportedMode` itself for unknown mode numbers, and `Success` without calling the automation if the controller asks for the current mode. If the main loop does not answer within 750 ms the response is `GenericFailure` ("Timed out").

**Mode Select** is different: the SDK handles `ChangeToMode` itself (the only possible answers are success and a constraint error), and `on_change_to_mode` is a notification, `matter.mode.reject` has no effect. Mode Select also needs a `description`, and its semantic tags are `{mfg_code, value}` pairs:

```yaml
matter:
  endpoints:
    1:
      mode_select: {}
      clusters:
        mode_select:
          description: Fan preset        # required, 1-64 characters
          modes:
            - {label: Low, tags: [{mfg_code: 0xFFF1, value: 1}]}
            - {label: High}
          select: fan_preset
```

## matter.mode.set

Sets `CurrentMode` from an automation (when no select is bound, or from a lambda):

```yaml
- matter.mode.set:
    endpoint: 1                      # a number or an endpoint id
    cluster: rvc_run_mode            # conf key of the cluster
    mode: 1                          # templatable
```

# Operational State and RVC Operational State

```yaml
clusters:
  operational_state:            # or rvc_operational_state
    phases: [Pre-wash, Wash]    # optional PhaseList (without it PhaseList is null)
    states:                     # optional: more states than the mandatory ones
      - {id: 0x80, label: Soaking}   # manufacturer state 0x80-0xBF with a label
    state: washer_state         # select or text_sensor that reports the state
    state_map: {Idle: stopped}  # source value -> state name (optional)
    phase: washer_phase         # select or text_sensor that reports the phase
    countdown_time: remaining   # sensor in seconds
    on_start: [...]             # operational_state only
    on_stop: [...]              # operational_state only
    on_pause: [...]             # together with on_resume
    on_resume: [...]
    on_go_home: [...]           # rvc_operational_state only
```

`OperationalStateList` contains the mandatory states (`stopped`, `running`, `paused`, `error`; RVC adds `seeking_charger`, `charging`, `docked`) plus the ones in `states:`. The optional RVC states are `emptying_dust_bin`, `cleaning_mop`, `filling_water_tank`, `updating_maps`.

## Commands

A command only exists in the data model, and is only advertised to controllers, when its trigger is configured: `Pause` and `Resume` come together (the specification makes one mandatory when the other exists), `Start` and `Stop` exist only on `operational_state`, `GoHome` only on `rvc_operational_state` (the RVC cluster has no Start/Stop; use the RVC run mode to start and stop cleaning). The SDK already refuses commands that do not fit the state (for example `Pause` while stopped, answered with `CommandInvalidInState`) and does not call the automation when nothing has to change (`Pause` while paused).

The command is answered with `OperationalCommandResponse`. `NoError` is the default; reject in the automation to return an error state:

```yaml
on_start:
  - if:
      condition:
        binary_sensor.is_on: washer_door_open
      then:
        - matter.operational_state.reject:
            error: unable_to_start_or_resume     # name or a manufacturer number 0x80-0xBF
            label: Door open
            details: Close the door first
  - switch.turn_on: washer_start
```

The same 750 ms rule as for the modes applies (`unable_to_start_or_resume` for `Start`/`Resume`, `unable_to_complete_operation` for `Stop` and `command_invalid_in_state` for the others on timeout).

The state does not change by itself after an accepted command: the appliance reports it through `state:` or `matter.operational_state.set`.

## Reporting the state

`state:` binds a select or a text sensor. Its value is matched against the state names (case-insensitive, `_`, `-` and spaces are ignored): `stopped`, `running`, `paused`, `error`, the ones in `states:` (manufacturer states are matched by label) and the aliases of `state_map`. Select options are checked against that list when the config is validated. `phase:` works the same with the names in `phases:`; an empty value or `none` makes `CurrentPhase` null.

The state `error` can only be entered by raising an error. A source that reports `error` raises `UnableToCompleteOperation`; use the action for a specific one.

Actions:

```yaml
- matter.operational_state.set:        # state and/or phase, templatable strings
    endpoint: 2
    cluster: operational_state         # default
    state: running
    phase: Wash

- matter.operational_state.error:      # OperationalError event, state becomes Error
    endpoint: 1
    cluster: rvc_operational_state
    error: stuck                       # name or number
    label: Wheels stuck
    details: Left wheel

- matter.operational_state.completed:  # OperationCompletion event
    endpoint: 2
    completion_error: no_error         # default
    total_operational_time: 3600       # seconds, optional
    paused_time: 120

- matter.operational_state.reject:     # only inside on_start/on_stop/on_pause/on_resume/on_go_home
    error: command_invalid_in_state
```

Error names: `no_error`, `unable_to_start_or_resume`, `unable_to_complete_operation`, `command_invalid_in_state`, plus on the RVC `failed_to_find_charging_dock`, `stuck`, `dust_bin_missing`, `dust_bin_full`, `water_tank_empty`, `water_tank_missing`, `water_tank_lid_open`, `mop_cleaning_pad_missing`, `low_battery`, `cannot_reach_target_area`, `dirty_water_tank_full`, `dirty_water_tank_missing`, `wheels_jammed`, `brush_jammed`, `navigation_sensor_obscured`.

`countdown_time` feeds `CountdownTime` (null while the sensor has no value). Changes are reported by the SDK with the quieter reporting rules of the cluster.

# Laundry Washer Controls

The spin speeds and rinse options of a washer:

```yaml
clusters:
  laundry_washer_controls:
    spin_speeds: ["Off", "400", "800", "1200"]   # SpinSpeeds (strings, max 16, each 1-64 bytes); enables the spin feature
    spin_speed: washer_spin                      # select (options = spin_speeds), SpinSpeedCurrent <-> select
    rinses: [none, normal, extra]                # SupportedRinses (none, normal, extra, max); enables the rinse feature
    number_of_rinses: washer_rinses              # select (options = the rinse names), NumberOfRinses <-> select
```

The lists are what the SDK checks controller writes against (`SpinSpeedCurrent` is an index into `spin_speeds`, `NumberOfRinses` must be one of `rinses`), so a controller can not set something the machine does not offer. A write that the SDK accepted sets the select; changing the select updates the attribute. `NumberOfRinses` starts with the first rinse of the list, `SpinSpeedCurrent` is null until the select has a state. The Temperature Control cluster of a washer (temperature levels) still has no delegate.

# Threading

SDK callbacks run on the CHIP task, ESPHome on the main loop:

| Direction | Mechanism |
|---|---|
| Matter command -> ESPHome | The CHIP task posts the automation to the main loop and waits at most 750 ms for its synchronous part. Nothing is posted when there is no automation or select (the command is then accepted at once). |
| ESPHome -> Matter | `run_on_matter_thread` (modes: `Instance::UpdateCurrentMode`; operational state: `SetOperationalState`, `SetCurrentPhase`, the event functions). Mode Select uses a normal attribute write. |

An automation that is slow (waits for hardware) should answer from a state it already knows and do the slow work after a `delay:`/`script`.

# Conformance

`python -m tools.conformance <config.yaml>` knows what the delegate layer adds: `SupportedModes`, `CurrentMode`, `ChangeToMode`, `ChangeToModeResponse` for the mode clusters, the configured commands plus `OperationalCommandResponse` and the `OperationalError`/`OperationCompletion` events for the operational state clusters. A delegate-driven cluster without a configuration is reported (`CL-CMD-MISSING`, `CL-ATTR-MISSING`), exactly like the endpoint behaves.

Not covered yet: Energy EVSE, Device Energy Management, Service Area, Laundry Dryer Controls, Dishwasher Alarm, Temperature Control (delegate) and Oven Mode / Oven Cavity Operational State (not available in esp-matter 1.6). The `oven_mode` cluster is listed in the data model but rejected because esp-matter has no such cluster.
